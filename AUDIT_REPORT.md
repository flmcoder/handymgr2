# HandyManager Pre-Change Audit

**Scope:** Static review of the checked-out application, database schema/migrations, Express routes, browser fetch/render paths, available tests, and the supplied Render log excerpt. No application code was changed. No SQL was executed against the production/tunnelled database and no Render Shell command was run; the recurring failure is attributable from the emitted SQL and repository schema definitions without risking a production write.

**Evidence caveat:** No `render-errors.log` file was present in the workspace. Runtime analysis below is based on the pasted log attachment and source at the current checkout. Source citations use `path:line` notation.

## Executive Summary

1. **Recurring bill sync failure (confirmed):** PostgreSQL `42703` is raised because the Drizzle schema and bill upsert include four columns that the runtime `CREATE TABLE IF NOT EXISTS` and the historical bill-cache migration omit: `work_order_id`, `cash_account_id`, `posting_date`, and `account_number`. The table already exists, so `IF NOT EXISTS` does not repair its definition. `v0:bills` has therefore failed repeatedly with zero rows written.
2. **Vendor page likely cannot authenticate:** `/api/local` routes are globally protected by `pmScopeMiddleware`, but `fetchVendors()` does not send the bearer token used by the neighboring property/work-order callers. Its catch clears the vendor list and returns `false` without logging the error.
3. **Work-order data defects:** sync only maps the first nested `AssignedUsers` entry into assigned-user columns; direct assignment fields are not a fallback there. Later API normalization supplies `updated_at` as both completion dates, masking the separately stored completion fields.
4. **Dispatch split-queue defect:** the API returns `branch`, but `getDispatchQueueBranch()` ignores it and tries to rediscover the branch by matching the queue row to the browser's currently loaded `WORK_ORDERS` list. Rows not in that list can disappear from Phoenix/Tucson queue views.
5. **Other pasted HTTP entries:** `/system/ping` is not the implemented health route (`/health`), so that HEAD 404 suggests a probe path mismatch. Requests for `.env*`, WordPress paths, and `robots.txt` are consistent with unsolicited scanners; there is no evidence in the excerpt that secrets were returned. Root-page GETs are expected static-site requests; POST `/` is not a defined application route.

## 1. Render / Runtime Log Analysis

### 1.1 Confirmed recurring PostgreSQL failure: `v0:bills`

The repeated runs share SQLSTATE **`42703` (undefined column)** and fail on an insert into `appfolio_bills`. The logged insert names 20 columns; the supplied parameter list is consistent with a bill row and does not indicate malformed parameter count or date/amount conversion. In particular, the repository's `normalizeBillSyncRow()` accepts the logged AppFolio fields (`Id`, `Reference`, `ApprovalStatus`, `TotalAmount`, `InvoiceDate`, `DueDate`, `CashAccountId`, `LastUpdatedAt`) at `backend/sync/billSyncPolicy.ts:52-78`.

| Evidence | Location | Finding |
|---|---|---|
| Declared schema | `backend/schema.ts:54-76` | `appfolioBills` declares `work_order_id`, `cash_account_id`, `posting_date`, and `account_number`. |
| Runtime initializer | `backend/server.ts:946-972` | `ensureBillsTable()` creates the table with `CREATE TABLE IF NOT EXISTS`, but the definition only includes columns through `updated_at` and never runs `ALTER TABLE ... ADD COLUMN` for those four fields. |
| Historical migration | `db/migrations/2026-09-03_appfolio_bills_cache.sql:1-21` | The bill-cache migration has the same older definition and does not add the four later schema fields. |
| Failing write | `backend/sync/repositories.ts:355-398` | `upsertBills()` inserts the normalized Drizzle record and its conflict-update set references every newer field. Drizzle consequently includes the undeclared columns in generated SQL. |
| Startup path | `backend/server.ts:10985-10993` | Startup runs other sync/work-order repairs and then calls `ensureBillsTable()`; no bill-column repair is called. `CREATE TABLE IF NOT EXISTS` leaves an existing old table unchanged. |

**Root cause:** deployed database schema drift, not an invalid upstream bill. A missing-column SQLSTATE can be raised for any of the four schema-only fields; the emitted error omits the PostgreSQL column detail, so the log alone cannot distinguish which missing column PostgreSQL resolves first. The code establishes the set of candidates definitively.

**Why it repeats:** `runSync()` archives/checkpoints the fetched page, attempts the repository upsert, and catches the error at `backend/sync/syncRunner.ts:403-425`, logs a failed run, finalizes it as failed, and returns a failed summary. Since the failed run is not a successful cursor checkpoint, the scheduler keeps using the last successful `v0:bills` cursor. The same eligible bill is fetched and fails again on subsequent scheduled cycles.

**Impact:** bill sync has `upserted=0`, `pages=0` in the scheduler summary despite receiving the page; cached bill data becomes stale, and features dependent on bill links/amounts (billing, vendor spend, and closure matching) may be incomplete. The scheduler's `skipped scheduled tick because the previous cycle is still running` line is a separate overlap guard at `backend/server.ts:10797-10810`; it means a prior sequential cycle exceeded the interval, not a distinct database exception.

### 2.3 Normalization patterns and gaps

- DB rows are deliberately snake_case; the Express server normalizes selected fields for legacy frontend consumers instead of serializing Drizzle camelCase. `normalizeWorkOrderRow()` spreads raw JSON and overlays a stable snake_case API contract (`backend/server.ts:3821-3860`). This is generally sound, but the overlay currently mislabels completion dates.
- Most frontend code maps API snake_case into camelCase before rendering; the table above lists proven exceptions rather than treating every casing difference as a defect.
- Many API results preserve `raw_json`, which can provide fallback values. A raw payload is not a substitute for projecting/normalizing fields that the UI relies on, and relying on raw aliases can vary by AppFolio payload version.

## 4. UI / UX & State Debt

### Confirmed gaps

- **Vendors lack a load/error state:** `fetchVendors()` sets a global API status to “Loading” but its failure path empties data and returns false without restoring a specific error state (`src/app.js:7423-7495`). The table renderer only shows “No vendors loaded” or “No vendors match filters” (`22822-22956`). This combines with the missing bearer token to mask a likely 401.
- **Properties lack a load/error/empty distinction:** failed property fetch clears all property data (`src/app.js:7499-7589`); downstream dropdowns can appear legitimately empty.
- **Work-order empty message conflates offline with no data:** `renderWorkOrders()` displays “No work orders loaded. Connect to API or import a cache file” when active plus inactive arrays are empty (`src/app.js:19068-19074`), even though `fetchWorkOrders()` has a specific error in source state (`6543-6627`). Differentiate loading, empty, and failed states.
- **Billing best-effort calls hide the upstream error:** background AP/close-assist load catches and ignores bill failure (`src/app.js:26636-26638`, `26701-26710`). The user may see missing bill-linked values without a local explanation.
- **Dashboard chart errors produce blank/partial widgets:** `src/dashboard.ts:1550-1738` logs errors and hides chart loading indicators; there is no consistent empty/error chart state. The work-order fallback logs at `1710-1738` and continues with zero rows.
- **Dispatch live poll can leave stale UI looking live:** `_pollLive()` swallows exceptions and does not mark its live indicator stale/error (`src/app.js:30054-30076`). Manual refresh does surface an error at `29820-29900`.
- **Null/shape fallbacks are uneven:** `src/app.js` frequently reads nested/optional row fields directly. Many renderers do use `|| ''`, `|| '—'`, or `params.data || {}`, but safety does not fix silently absent API fields (vendor fields and bill work-order link above). Prefer contract validation at fetch boundaries over adding optional chaining alone.
- **Potential external-probe confusion:** `/system/ping` is not a route; the implemented `/health` is. `/robots.txt` also has no file. These produce operational noise/monitor false alarms rather than broken app DOM.

### DOM binding review

- The work-order grid search input is dynamically created and its `input` handler is bound in `renderWorkOrdersGrid()` (`src/app.js:18749-18817`). The renderer destroys/replaces grid/board structures on view changes and has an update-in-place branch, so static inspection does **not** prove duplicate listeners or a specific missing element ID. Add a focused browser regression test if modifying that lifecycle; do not classify this as a confirmed broken binding based on current evidence alone.
- Dispatch queue renderer explicitly checks required queue containers and warns if absent (`src/app.js:28174-28185`); roster/grid renderers similarly no-op if target bodies are absent. `index.html:1654-1704` contains matching queue and roster IDs with initial loading placeholders. No definite ID typo was found in these audited primary views.
- The confirmed broken binding is semantic rather than DOM-ID based: dispatch queue’s branch resolver discards server-provided row `branch` and recomputes from an incomplete browser-side work-order cache (`src/app.js:27922-27938`).

## 5. Prioritized Action Plan

### P0 — Sync failures / render-blocking defects

1. **Repair bill-table schema drift.** Add an idempotent migration/repair for `work_order_id`, `cash_account_id`, `posting_date`, and `account_number`; call it before scheduler startup and any bill upsert/query. Align `ensureBillsTable()` and the historical migration with `backend/schema.ts`. Verify live schema with read-only `information_schema.columns` before/after; then run one bounded `v0:bills` sync and confirm a completed page/upsert. Add regression coverage that checks schema-repair SQL includes every Drizzle bill column. **Do not simply reset the bill cursor.**
2. **Check full billing consequences after repair.** Re-run the failed date window/backfill safely and confirm billing/vendor-spend/closure-candidate queries see the previously skipped bill population. Assess idempotency and avoid overwriting newer records while replaying.
3. **Confirm monitoring path.** Change any configured `/system/ping` probe to `/health` (or add a deliberate compatibility alias) and verify expected status during DB up/down. No other pasted HTTP status is a confirmed application outage.

### P1 — Missing or mismatched data / recoverability

1. **Fix vendor auth and error contract.** Pass the bearer token in `fetchVendors()`; preserve prior data or show explicit retry/error UI instead of clearing the list silently. Verify manager/PM scoped sessions and unauthorized behavior.
2. **Correct work-order assignment mapping.** Normalize both nested `AssignedUsers` and direct `AssignedUserId`/`AssignedUserName` variants (plus supported nested `UserId`/`FullName` aliases); add tests for empty/missing/nested/direct cases.
3. **Preserve actual completion fields through API.** Select/serialize `completed_on`, `work_completed_on`, and `canceled_on`; stop aliasing `updated_at` to completion dates. Add endpoint/normalization tests and validate timeline/history dates.
4. **Honor server-provided dispatch branch.** In `getDispatchQueueBranch()`, prefer normalized `row.branch` and/or `row.property_group_uuid` before attempting a browser-side work-order join. Add tests for queue rows absent from `WORK_ORDERS` and for both split branches.
