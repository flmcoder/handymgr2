Database API (v0)
API Overview

The API utilizes a RESTful architecture, allowing you to query and manage data from the AppFolio ecosystem. All API requests and responses are formatted in application/json, and HTTP Basic Auth is used to verify a user's identity. The base URL for all API requests is https://api.appfolio.com/api/v0/{endpoint}.
To kick start your API usage, we recommend diving into our Getting Started section(s), depending on your selected authentication flow. Depending on your selected authentication flow, this section takes you through a standard API use case. Review the API Best Practices section to optimize your API usage and ensure seamless integration into your application.

Authentication
HTTP Basic Authentication
HTTP Basic Authentication is a simple authentication scheme where credentials (Client ID and Client Secret) are encoded in Base64 format and included in each API request's header, requiring separate credential pairs for each customer database you need to access. While still supported, Basic Authentication requires:
Separate credentials for each customer database Manual onboarding process for each new customer Storing permanent credentials securely
Managing multiple sets of credentials across different customer databases
Required Headers

NameFormatValueAuthorizationstringBasic {ENCODED-STRING}X-AppFolio-Developer-IDstring{YOUR-DEVELOPER-ID}Getting Started: HTTP Basic Authentication
1. Get Your Developer ID
Select your account name ? Admin ? Developer ID in the Developer Details card
1. Get Your Basic Auth Credentials
Beneath API Credentials, select Basic Auth
Generate and securely store your Client Secret on the same row by selecting Generate a Client Secret. Store this value in a safe place.
1. Generate the Base64 Encoded Credentials
For Mac users, paste the following command with your Client ID and Client Secret in Terminal:
echo -n "{ClientID}:{ClientSecret}" | base64

For Windows users, paste the following command with your Client ID and Client Secret in Windows Command Prompt:
powershell "[convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("{ClientID}:{ClientSecret}"))"

Replace in the above commands:
{ClientID} with your Client ID
{ClientSecret} with your Client Secret
1. Make an API Request
curl -g --request GET 'https://api.appfolio.com/api/v0/{resource}/' \
--header 'X-AppFolio-Developer-ID: {YOUR-DEVELOPER-ID}' \
--header 'Authorization: Basic {YOUR-ENCODED-STRING}'

Replace in the above command:
{YOUR-DEVELOPER-ID} with your Developer ID
{YOUR-ENCODED-STRING} with the value returned from step 3
{resource} with the desired resource (for example, properties, tenants, or charges)
Note: You'll need separate credentials for each customer database when using Basic Auth.

Rate Limits
To prevent network congestion and avoid 429 Too Many Requests errors, we recommend regulating or staggering the rate of your requests. All endpoints have per-second, per-minute and per-hour rate limits for each set of credentials.
Currently, the rate limits are as follows:
8 requests per second, 256 requests per minute, and 4096 requests per hour

API Best Practices
To maximize efficiency and ensure the reliability of your integration with the API, review the following best practices.

Date and Time Formatting
Our API strictly adheres to the ISO 8601 format for <date-time> representation, which follows the pattern YYYY-MM-DDTHH:mm:ssZ for date and time, where "T" separates the date and time components, and "Z" indicates Coordinated Universal Time (UTC). This global standard ensures clarity and consistency across different systems and programming languages. By following ISO 8601, developers can avoid ambiguity and facilitate seamless integration with our API.
YYYY-MM-DDThh:mm:ssZ

YYYY is the four-digit year MM is the two-digit month DD is the two-digit day
T separates the date and time components
hh is the two-digit hour mm is the two-digit minute ss is the two-digit second
Z indicates Coordinated Universal Time (UTC)
2022-06-00T12:00:00Z is equivalent to June 1st, 2022, at 12:00:00 PM UTC.

Deprecation
When reading the API documentation you will notice attributes marked as Deprecated. When an attribute or endpoint is marked as Deprecated, we no longer recommend using it due to changes in the API.
Any new API users should not use deprecated attributes, and existing API users should consider transitioning to updated attributes or endpoints. When a new API version is released in the future, the deprecated attributes or endpoints will be removed entirely.

Filtering and Pagination
To ensure the proper utilization of the LastUpdatedAt query parameter, we recommend the following best practices:
The LastUpdatedAt attribute indicates the date of the most recent update to an object in the AppFolio Property Manager. However, changes may not always be visible to API users, as they could involve internal attributes or attributes that are inaccessible to certain users. API users should not make assumptions about what changed on an object based solely on the fact that LastUpdatedAt has changed. Rather, they should compare the changed object's attributes to the last known attributes to discover the change if needed.
For the first import using a given endpoint, you may want to set the LastUpdatedAt filter to a date in the past (e.g. filters[LastUpdatedAtFrom]=1970- 01-01T00:00:00Z) and use the response to sync up your internal records. If this response has more than one page, you will need to fetch the following pages as well. For subsequent requests following the initial import, avoid setting arbitrary parameters for LastUpdatedAt and instead set this value to the last time you made a successful request. This will improve performance by only retrieving the data you need, and subsequently reducing the time it takes to receive the response.
To ensure the proper utilization of the page query parameter, we recommend the following best practices:
If possible, use the default value for the page query parameter. The default values were carefully selected to ensure that unnecessarily large requests are not sent. The default value for the page size parameter is 1000, but this might differ per endpoint. The page size parameter can be modified to a smaller number if desired. If page sizes larger than the default page size parameter are requested, page size will be reduced to the default value. AppFolio can reduce or increase the default page size parameter for a given endpoint.
The following is an example of a valid request with the default values for the page query parameter:

https://api.appfolio.com/api/v0/{resource}?filters[LastUpdatedAtFrom]=1970-01-01T00:00:00Z&page[number]=1&page[size]=1000

Outages
As with any API, errors and exceptions will occur. For example, there may be a connection error between servers or a rare outage. Always watch for errors and exceptions, and if they do occur, log the request in as much detail as possible. This will reduce response times in the event that you need to contact support.
In the event of a 503 Service Unavailable error, we suggest implementing Exponential Back Off. This ensures that your server does not generate excessive load.
A 533 Data Unavailable error typically occurs when a database is down due to database migrations and/or scheduled maintenance. Scheduled maintenance errors will typically resolve within five minutes, and will occur between 9PM and 4AM PST.

Retry-After Header: Retrying Rate Limited API Requests
A Retry-After HTTP response header is utilized by AppFolio to manage rate-limited API requests. When your request is rate limited, this header indicates the time duration in seconds that you should wait before resending the request. It is best practice to observe the value of the Retry-After header and wait for the specified time to resend the request. Adhering to this guidance will reduce the number of 429 "Too Many Requests" errors sent, and conserves resources for both your integration and AppFolio's services.
Rate Limits and Error Responses:
For each set of credentials, AppFolio enforces rate limits as follows: 8 requests per second
256 requests per minute 4096 requests per hour
Should any of these limits be exceeded, AppFolio will trigger a 429 "Too Many Requests" error and include a Retry-After header.
If you send more than 8 requests in a second, the value of the Retry-After header will be 1 second.
If you send more than 256 requests in a minute, the value of the Retry-After header will be < 60 seconds.
If you send more than 4096 requests in an hour, the value of the Retry-After header will be < 3600 seconds.
Rate Limit Resets and Handling Time-Related Errors:
All rate limits reset at the beginning of each new second, minute, or hour. In scenarios where the per-minute or per-hour rate limits are exceeded, the Retry-After header's value specifies the time remaining until the next complete minute or hour when the 429 Too Many Requests error will expire, and new requests should be sent.
Example Scenario:
For instance, if you sent 300 requests at 09:49:30 AM, the Retry-After header would display 30 seconds. The next request should be scheduled at or after 9:50:00 AM. If the per-hour rate limit is exceeded, the 429 error will expire at the top of the upcoming hour, regardless of the time it was triggered. As an example, sending 5000 requests at 09:15:00 AM would lead to a Retry-After header value of 2700 seconds, necessitating a wait until 10:00:00 AM before you should issue another request.

User Roles
In order to successfully carry out certain requests using the API, the correct user roles must be enabled in the AppFolio Property Manager. Some examples include:
When assigning a lead to a user, that user must have the Leasing Agent role in the AppFolio Property Manager.
When creating a work order, the assigned user must have the Maintenance Tech role in the AppFolio property manager.
If a user does not have the correct permissions your request will result in a 422 "User not found." error.

API Troubleshooting

When troubleshooting issues associated with the API, ensure you can answer Yes to the following questions in the checklist. If you answer No to any of the following questions, it is likely that you have found the problem.
1. Is the URL correct?
A valid URL should look similar to http://api.appfolio.com/api/v0/{endpoint}.
1. Were the correct credentials passed in the request?
Ensure the Client Secret and Client ID belong to the same database whose records you are trying to access.
1. Is the authorization header valid?
Ensure the formatting of the Client ID and Client Secret passed into your authorization header are valid.
1. Are the correct User Roles enabled?
For example, if you are creating a lead and assigning a user to that lead, does the user have the Leasing Agent role enabled?
1. Are the request parameters valid?
If an incorrect parameter value was passed, the returned error codes should be descriptive enough to assist you in identifying the problem.
1. Is the rate at which you are issuing requests regulated?
If multiple PATCH requests are made to the same resource simultaneously, the first request will update the resource but the second request to update the resource will fail. Thus, it is important to spread out or queue your PATCH requests across resources.
In general, staggering the rate at which you issue requests will prevent network congestion and errors.

Webhooks Overview
AppFolio provides support for webhooks through the API. Webhooks are HTTP-based callback functions that allow your app to receive real-time updates about events in the AppFolio system. Webhooks are only available for a small subset of endpoints and can be enabled by reaching out to an AppFolio representative.
You must configure a webhook URL to allow your application to receive webhooks. Once a webhook URL is configured, you will subscribe to a specific webhook topic and receive notifications about that event once it occurs in the AppFolio system. For example, when a user creates, updates, or deletes a property within AppFolio, a webhook callback from AppFolio will notify your application about the property event.

Why Use Webhooks?
Webhooks provide real-time updates that prevent you from having to periodically query the API, contributing to cost savings in infrastructure and server resources
Webhooks make it easier for you to adhere to our rate limits by removing the need to periodically poll for changes
Webhooks can allow you to automate workflows in your organization by giving you the ability to define how to respond to webhook event notifications that you receive

Authentication
Webhook event notifications are sent to an endpoint defined and exposed by you. The webhook URL you define must be secured by HTTPS. To validate that the webhook event notifications are coming from AppFolio and verify the integrity of the notification's content, AppFolio implements JSON Web Signature (JWS) message signing with a detached payload. The X-JWS-Signature header contains the signature for the webhook payload.
You must verify the signature of each webhook and discard all webhook payloads that fail signature verification without processing them. The step-by- step guide to verifying the signature can be found in the Webhooks: Getting Started section along with sample code in several languages.

Webhook logs are only accessible by a user with the Administrator role. This step-by-step guide walks you through enabling webhooks. The steps include configuring your application to receive notifications, subscribing to webhook topics, and how to start receiving webhook event notifications.

Configure a Webhook URL
The Webhook URL is a server for incoming HTTP POST notification messages triggered by events within the AppFolio system. The URL must be secured by HTTPS, and the domain has to be owned by your company.
1. Navigate to the Webhook Card within Admin Settings. As a user with the Administrator role, select Admin from the User drop-down in the top- right corner of the page.
2. Navigate to the Webhooks Card at the bottom left of the page.
3. To add a Webhook URL, select Edit from within the Webhooks Card. The Webhook URL will become configurable.
4. Enter the name of your Webhook URL.

Subscribe to Webhook Topics
After webhooks are enabled for your integration, you will be given access to a subset of webhook topics. A webhook topic refers to a specific event or category of events that can trigger a webhook. The topics you can subscribe to will be listed beneath Topic Subscriptions.
1. From the list of topics available for subscription, select the ones you are interested in enabling by selecting the checkbox adjacent to the webhook topic.
2. Ensure your Webhook URL can receive an event notification by selecting Send Test Event.
3. If your Send Test Event was successful, an entry will appear in the webhook logs that the test was successful.
4. Navigate to the Webhook Logs page and ensure the test event is timed correctly.
5. The See All Events link will point you to displaying all webhook events you can utilize to debug errant requests.
Important: Once you have subscribed to a topic, it is time to set up your web server to receive HTTPS POST requests from AppFolio. When setting up your web server, ensure that the server is behind the HTTPS URL configured in Step 2.

Verify the Webhook Message Signature
AppFolio signs all outgoing webhooks to enable recipients to verify the authenticity and integrity of the received notifications. You must verify the webhook message signature in the event notification payload sent by AppFolio by executing the following steps. Any notifications that fail the webhook message signature verification must not be processed.
1. Fetch Public Keys From AppFolio
Configure a verification library to obtain public keys from https://api.appfolio.com/.well-known/jwks.json. The endpoint will respond with a set of keys in JSON Web Key Set (JWKS) format:
1. Read the Payload of the Webhook Request Sent by AppFolio
This is a sample request that will be sent to your webhook. Notice the payload and the signature header.
POST / HTTP/1.2
Host: example.appf.io
Content-Type: application/json
X- JWS-Signature:    eyJhbGciOiJQUzI1NiIsImlhdCI6MTY5MzI2NDcwNywia2lkIjoiNWViZGMxMjgtMGZmOC00YzRiLTllNzAtZGU3MjBkY2M2ZjEyIiwiY3JpdCI6WyJiNjQiXSwiYjY0IjpmYWxzZX0..CmenfU2_

{
"client_id":"{your-client-id}", "event_id":"0f56aa84-e319-4460-89b2-2be2f6d12345", "topic":"properties",
"resource_id":"5b4afdd0-25af-11ee-8c46-06b43963c6f4", "event_timestamp":"2023-03-27T16:55:12Z", "message_sent_at":"2023-08-28T23:18:27Z", "event_type": "create"
}

1. Extract the JWS Header from the signature. This is before the .. in the X-JWS-Signature header value.
2. Extract the JWS Signature. This is after the .. in the X-JWS-Signature header header value.
3. Compute the JWS Payload. Encode the body of the main request (the payload) using the unpadded alternate base64 encoding defined in RFC 4648. Additionally, ensure you are using the unparsed raw contents of the HTTP body, as processing like JSON parsing could reformat the body and cause the verification to fail.
4. Verify the Webhook Message Signature
Concatenate the encoded values from steps 3, 4, and 5 with . as a separator. For example:

jws-header + "." + jws-payload + "." + jws-signature`

Pass the JWS Signature, the JWS Header, and the JWS Payload to the JWS verification library you configured with AppFolio's JWKS public keys in
Step 1. Code samples in various languages can be found in this repository. This should result in a successful verification.
Note: AppFolio uses RSASSA_PSS_SHA_256 as the signature algorithm. For additional information pertaining to this algorithm, click here.
